The database layer should own anything that directly works with SQLite, like connect, create_tables, seed_sample_data, the get_... query functions, get_all_enrollment_records, and the raw SELECT, INSERT, and UPDATE statements. These functions mostly deal with creating tables, storing rows, reading rows, or updating rows, so they belong in a future database/store class. The service layer should own the student actions and rules. enroll_with_key belongs there because it checks the student information, looks up the enrollment key, and decides how enrollment should happen. soft_unenroll_student also fits the service layer because it follows the rule that students are marked as "unenrolled" instead of deleted. get_student_summary belongs in the service layer too because it turns raw enrollment records into useful summary counts.


The mixed parts are the areas that combine too many responsibilities. enroll_with_key mixes service rules with database updates, so later the service should make the decision and the database class should save the row. export_database_snapshot is mixed because it reads database data and writes a JSON file, so it could become a separate helper or export method. The constants like DB_PATH, SNAPSHOT_PATH, statuses, sample course keys, and current student are okay for a starter file, but they should eventually move into config/constants. The main runner is also mixed because it sets up the database, seeds data, tests enrollment, prints results, and exports the snapshot. A simple future design would be: database class handles SQL and rows, service class handles enrollment rules and student actions, and runner/config code handles setup and testing flow.
